Fridge Door Companion — App Map

A take-home guide to the finished proof of concept: what it does, where the code lives, and where to start when you want to change something.

What this app is

Fridge Door Companion keeps your whole kitchen on one screen. A fridge sits on the left, the ingredient tray beside it, and My Recipes directly under the fridge. You tap or drag ingredients into the fridge and enter how much you have; press My Recipes and the app ranks its built-in recipes against your stock, showing the best 2–3 picks with a “You have 4/5 · Missing: 1” fit line. Open a pick and Cook this to deduct what you used — when the recipe is missing something, Generate the shopping list also appears, and you check items off as you buy them. Everything is stored in your browser’s localStorage — there is no backend and no account.

The main pieces — five files, no build step

  • index.htmlthe single fridge-door screen — structure only, all content is rendered by app.js
  • styles.cssall of the look: the stage (fridge in the middle, category bubbles in two columns around it), the door's 3D swing, the cards, and the CSS keyframe animations
  • app.jsthe logic in three sections: pure logic (stock math, scoring) → store (localStorage) → UI (rendering and events)
  • data/ingredients.js32 built-in ingredients — 28 tracked in the tray, 4 marked staple: true (salt, sugar, flour, milk) that are assumed always on hand
  • data/recipes.js35 built-in recipes; every ingredient they call for exists in the tray
  • verify/slice-1..4.jsfour node harnesses (120 assertions) that run the pure logic without a browser

One action, end to end — pressing “Cook this”

A route through the code — reference route, prepared from the finished code (not yet walked through together)

Stop 1 — the entry point: app.js, search onCookThis

What happens when you press “Cook this”. It reads what will leave the fridge (cookDeductions) before committing, calls cookRecipe, saves the new state, re-renders the door, then plays the combining animation and the “Out of the fridge” float. Reading the deduction first is why the floating numbers can never drift from what actually happened.

Stop 2 — the rule: app.js, search function cookRecipe

The deduction rule, in pure logic with no DOM and no storage. Each ingredient you actually have is reduced by the recipe amount — the full amount when there is enough, otherwise whatever is left, never below zero. Ingredients reaching 0 drop off the fridge display; missing ingredients are untouched; staples (salt, sugar, flour, milk) are never deducted. Because this section is pure, the same code runs under node in verify/slice-3.js.

Stop 3 — the visible result: app.js, search function playRemoveFloat

The chips you see rising off the fridge, one at a time. It anchors the float to the fridge's own position on screen, keeps the zig-zag inside the fridge's column, and unhides the layer before measuring the chips — a display:none parent reports zero-width children. The chips play one at a time, REMOVE_STAGGER_MS (500ms) apart, so a multi-ingredient cook reads as separate deductions. The animation itself lives in styles.css (@keyframes fdc-remove-rise, fdc-remove-fade).

The storage stop around all three: saveState / loadState in the same file, around the single versioned key STORAGE_KEY ('fdc-state-v1'). Storage is user data, so sanitizeState re-checks everything on load and falls back to a fresh kitchen if anything is corrupt.

To change this, start here

How strongly long recipes are favoured

LENGTH_BONUS in app.js (currently 0.1). The ranking weight is fit × (1 + bonus × tracked ingredients), so a three-ingredient recipe carries ×1.3 and a five-ingredient one ×1.5. After a change, run node verify/slice-2.js — it asserts the agreed weights and the order they produce.

What is on the ingredient tray, or what counts as a staple

data/ingredients.js. Add an ingredient with its categoryId, or mark one staple: true and it stops being tracked, scored, and shopped for. verify/slice-2.js checks every tray ingredient is used by at least one recipe and vice versa.

The recipe collection

data/recipes.js. Each recipe needs an id, name, dish emoji, ingredients (with amounts), and steps. The fit line, the green/red checklist, the shopping-list quantities, and the deduction all read from this one shape.

The starting categories, or the fridge/tray split

Categories: SEEDED_CATEGORIES in app.js (five: Produce, Dairy, Pantry, Leftovers, Meat & Fish). Layout: .fridge-stage + .bubble-field in styles.css — a 664 px stage capped at 900 px, bubbles placed at BUBBLE_X (17% / 83%) and bubbleSlotYs()'s vertical slots; the same markup turns into a column under the fridge below 1000 px. The door's swing is .fridge[data-open="true"] .fridge-door-panel { transform: rotateY(-100deg) }.

The buttons on a recipe card

renderRecipeView in app.js — search missingCount. The shopping-list button is toggled hidden when the open recipe is missing nothing, so a complete recipe shows “Cook this” alone; “Cook this” itself is always shown. verify/slice-3.js asserts the toggle is driven by the recipe’s missing count.

The wording of the empty states

renderRecommendations in app.js — the “Uh-oh — your fridge is empty, please refuel.” and “Unfortunately, there’s nothing fitting.” messages.

A practice to reuse

The moment: at the final review you asked for longer recipes to be favoured, because short ones win simply by being easier to complete. The change was made with its cost written down first — recorded in devpost/checklist.md under Revisions: bolognese (5/6, ×1.6) now outranks complete scrambled eggs (2/2, ×1.2), and that trade was accepted knowingly.

The evidence: the change then invalidated part of the proof. The built-in data no longer produced an equal-rank pair, so the fewest-missing tie-break — which the old fixture happened to exercise — was re-proved with a synthetic recipe pair instead. verify/slice-2.js now asserts it directly (“equal ranks still tie-break by fewest missing”).

The practice: when you change a rule, name the consequence you are accepting before you change it, then make the check prove the new rule. A fixture that passed for the old rule proves nothing about the new one — that gap is exactly where regressions hide.

Run it again

  • Start it: in the project folder run python3 -m http.server 8000, then open http://localhost:8000. (Any static file server works; there is no build step.)
  • Check it: node verify/slice-1.js through node verify/slice-4.js — 117 assertions, all run without a browser.
